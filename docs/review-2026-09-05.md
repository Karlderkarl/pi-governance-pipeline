## Findings

### F1 · Hoch · Reviewer-Retry verdrängt ein Critical

**Wo:** `skills/governance-pipeline/assets/auto-develop.sh:252-254` (`rank_of`), `:798-820` (Retry-Schleife).

**Was:** `--check` liefert 2, wenn ein Reviewer Findings hat, aber kein gültiges Verdict-Wort (`approve|reject`). Die Schleife retryt auch bei 2. Ein Retry, der sauber parst (Rang 0), ersetzt das Original (Rang 2), egal was drinsteht. Der Retry ist ein frischer Prozess ohne Erinnerung an den ersten Durchlauf und kann die Kritik schlicht nicht wiederfinden. Damit ist ein Original mit `verdict:"blocked"` und einem `critical` durch `{"verdict":"approve","findings":[]}` ersetzbar.

**Beleg (S1):** Stub-Reviewer `security` antwortet zuerst `{"verdict":"blocked","findings":[{"severity":"critical",...,"title":"RCE"}]}`, auf REMINDER `{"verdict":"approve","findings":[]}`. Ausgabe:

```
reviewer security retry taken (check 2 -> 0)
approved: issue-s1
```

`gate.json` enthält kein `RCE`. Das widerspricht der Doktrin "strictest wins", die gate.mjs und der Master-Parser sonst konsequent umsetzen. Der bestehende Smoke-Test `run-retry-keep` deckt nur den Fall "Retry ist Prosa" ab.

**Empfehlung:** Bei Rang 2 gar nicht retryen. Das Gate bewertet ohnehin nach Severity, das Verdict-Wort ist laut `prompt-builders.md` nur advisory; die Datei ist also bereits nutzbar. Alternativ: Retry nur übernehmen, wenn sein `worstRank` mindestens dem des Originals entspricht. `prompt-builders.md` (Abschnitt "Reviewer output schema") entsprechend anpassen.

### F2 · Hoch · Approve ohne Commit: Diff-Bleed und Stash-Verlust über Issues hinweg

**Wo:** `auto-develop.sh:937-944` (Approve-Zweig), `:1051-1060` (Issue-Schleife), `:946-996` (`take_over`).

**Was:** Der Approve-Zweig markiert das Issue als done und kehrt zurück. Der Arbeitsbaum bleibt ungecommittet. Das nächste Issue startet im selben Baum. Zwei Folgen:

1. `capture_diff` für Issue B enthält die Änderungen von Issue A. Drei Reviewer und der Master beurteilen fremden Code als Teil von B.
2. Fällt der Master bei B auf `take_over`, stasht `git stash push -u` auch die approvte Arbeit von A. Der Stash wird nie zurückgeholt. `tasks.md` und der State sagen weiterhin "A done".

**Beleg (S2):** Zwei Issues, A schreibt `a.txt`, B schreibt `b.txt`, B erhält im ersten Versuch `take_over`.

```
approved: issue-a
stashed working tree as pipeline: pre-take_over issue-b-...
approved: issue-b
```

Der erste Reviewer-Prompt von B enthält `WORK-OF-ISSUE-A`. Nach dem Lauf existiert `a.txt` nicht mehr im Arbeitsbaum, nur im Stash; `tasks.md` hat `- [x] issue-a`.

**Einordnung:** Der Commit-Schritt ist laut `SKILL.md:42` ein "marked stub". Im Approve-Zweig gibt es aber keine Markierung, nur den `auto-merge`-Hinweis. Wer das Skript unverändert mit mehreren offenen Tasks laufen lässt, verliert approvte Arbeit, ohne dass irgendwo eine Warnung steht.

**Empfehlung:** Mindestens ein expliziter `# ADAPT:`-Marker im Approve-Zweig. Darüber hinaus eine der drei Optionen: (a) vor dem nächsten Issue auf sauberen Baum prüfen und abbrechen bzw. warnen; (b) der Referenz einen Default-Commit geben (`git add -A && git commit -m "pipeline: <issue>"`), der über eine Variable abschaltbar ist; (c) ohne `--issue` nur ein Issue pro Lauf bearbeiten. Option (a) ist die kleinste Änderung, die den Datenverlust verhindert.

### F3 · Mittel · Severity-Listen müssen keine Partition sein

**Wo:** `assets/lib/governance.mjs:359-376` (`requireSeverityList`), `assets/lib/gate.mjs:191-197`.

**Was:** Der Validator prüft nur, ob jeder Eintrag eine bekannte Stufe ist. Ob `blocking ∪ followup` alle vier Stufen abdeckt, prüft niemand. gate.mjs sortiert ein Finding in `blocking`, wenn seine Stufe gelistet oder unbekannt ist, in `followups`, wenn gelistet. Eine bekannte, aber in keiner Liste stehende Stufe landet nirgends.

**Beleg:**

```
node gate.mjs --blocking critical --followup low --min-reviewers 2 r-high.json r-ok.json
-> "verdict": "clear", "blocking": [], "followups": [], exit 0
node governance.mjs config AGENTS.md   # review: { blocking_severities: [critical], followup_severities: [low] }
-> exit 0, keine Warnung zu den Listen
```

`contract.md:85` verspricht fail-closed für unbekannte Stufen. Für bekannte, ungelistete Stufen ist das Verhalten fail-open, und die Konfiguration ist per Tippfehler erreichbar (`[critical, hgih]` wäre ein Fehler, `[critical]` nicht).

**Empfehlung:** Im Validator: Vereinigung muss alle vier Stufen enthalten (Fehler), Überschneidung warnen. Zusätzlich in gate.mjs: eine bekannte Stufe, die in keiner Liste steht, blockt.

### F4 · Mittel · Guard: Redirection ohne Ziel-Prüfung blockt Lesezugriffe

**Wo:** `extensions/pipeline-guard.ts:59-68` (`shellWritesGovernance`), speziell `/>>?/.test(command)`.

**Was:** Sobald ein Governance-Dateiname irgendwo im Kommando steht und irgendwo ein `>` vorkommt, gilt das als Write. Das Ziel der Redirection wird nicht geprüft. Im Kind-Prozess der Pipeline (kein UI) wird das Kommando dann geblockt, solange nicht `PIPELINE_ALLOW_GOVERNANCE_WRITE=1` gesetzt ist. Die Rollen `research` und `implement` sollen SOUL.md und AGENTS.md aber lesen.

**Beleg (wörtliche Regex-Kopie):**

```
"cat AGENTS.md 2>/dev/null"    -> AGENTS.md     (geblockt)
"grep -n eval SOUL.md 2>&1"    -> SOUL.md       (geblockt)
"ls -la SOUL.md 2>&1"          -> SOUL.md       (geblockt)
"head -50 AGENTS.md > /tmp/x"  -> AGENTS.md     (geblockt)
"cat AGENTS.md"                -> (nicht geflaggt)
```

Der Guard ist erklärtermaßen ein Speed Bump, aber dieser Speed Bump steht auf dem Leseweg. Ein Agent, der gewohnheitsmäßig `2>&1` anhängt, verliert in jedem Lauf Tool-Calls.

**Empfehlung:** Die Redirection nur zählen, wenn ihr Ziel eine Governance-Datei ist, z. B. `/>>?\s*["']?[^\s"'|;&]*(SOUL|AGENTS|APPEND_SYSTEM|SYSTEM|CLAUDE|MEMORY)\.md/`. `2>` und `2>&1` explizit ausnehmen.

### F5 · Mittel · `AGENTS.override.md` ist ungeschützt

**Wo:** `pipeline-guard.ts:50` (`GOVERNANCE`), `auto-develop.sh:393` (`is_gov`), `:421-422` (Pathspec-Excludes), `:568-572` (`preserve_paths`).

**Was:** pi lädt `AGENTS.override.md` anstelle von `AGENTS.md`, und das Skript warnt zu Recht beim Start, wenn die Datei existiert (`:124-126`). Aber keine der drei Schutzschichten kennt die Datei: der Guard blockt weder `write`/`edit` noch `echo x > AGENTS.override.md`, `capture_diff` schließt sie nicht aus dem Review-Diff aus, `preserve_paths` rettet sie nicht über den Stash. Ein Implementer kann also die effektive Standing-Instruction jedes folgenden Kind-Prozesses schreiben, ohne dass ein Gate feuert. Gleiches gilt für `.pi/settings.json`, das mit `--approve` Extensions aktiviert.

**Beleg:**

```
"echo x > AGENTS.override.md"          -> (nicht geflaggt)
"cp x AGENTS.override.md"              -> (nicht geflaggt)
write/edit path AGENTS.override.md     -> (nicht geflaggt)
write/edit path .pi/settings.json      -> (nicht geflaggt)
```

**Empfehlung:** `AGENTS.override.md` (und der Vollständigkeit halber `AGENTS.MD`, `CLAUDE.MD`) in alle drei Listen aufnehmen. `.pi/settings.json` zumindest in den Guard.

### F6 · Mittel · Blocker-Eintrag enthält nicht die Findings, dafür alles andere

**Wo:** `auto-develop.sh:656-657` (`block_issue` mit `$(cat "$work/exclusions.md")`), `:259-274` (`blocker_history`).

**Was:** Beim Abbruch wird die komplette `exclusions.md` in MEMORY.md geschrieben: Lint-/Test-Logs und je 40 Zeilen Master-Auszug pro Versuch. Die eigentlichen Gate-Findings (`findings.md`, `gate.json`) fehlen. `governance-files.md:187` verspricht dagegen "the findings that were never resolved". `blocker_history` füttert die letzten fünf Einträge ungekürzt in Research- und Implement-Prompt zurück. `BLOCKER_HISTORY_MAX` deckelt die Anzahl, nicht die Größe. Mit einem chatty Linter wächst MEMORY.md pro Abbruch um bis zu 6 × 80 Zeilen, und der nächste Prompt ebenso.

**Beleg (S4):** Reviewer liefert konstant ein `high` mit Titel `REAL-FINDING`, Master rejectet, Budget läuft aus. MEMORY.md enthält 6 Master-Auszüge, aber kein `REAL-FINDING`.

**Empfehlung:** In den Blocker-Eintrag `findings_to_prose "$work/gate.json"` (bzw. `findings.md`) schreiben und von `exclusions.md` nur einen gekürzten Tail. In `blocker_history` die Ausgabe in Bytes deckeln.

### F7 · Niedrig · `take_over` ohne ersten Commit scheitert still

**Wo:** `auto-develop.sh:977-979`.

**Was:** `git stash push -u` verweigert in einem Repo ohne Commit ("You do not have the initial commit yet"). Das Skript fängt das mit `|| true` und schweigt. `implement_master` erbt den abgelehnten Baum, obwohl der Master genau das mit `take_over` verhindern wollte. Der Quickstart in `SKILL.md:31-38` erzeugt keinen Commit; der Zustand ist also der dokumentierte Erstzustand.

**Beleg (S3):** `git init` ohne Commit, Master gibt `take_over`. Keine Zeile "stashed working tree", `impl.txt` enthält danach zweimal `REJECTED-APPROACH`.

**Empfehlung:** Beim Start neben dem Repo-Check (`:118-119`) auch auf `HEAD` prüfen, oder im `take_over`-Zweig das Ausbleiben des Stash laut melden.

### F8 · Niedrig · gate.mjs stürzt bei `findings:[null]`

**Wo:** `gate.mjs:174-175`, `:113-114`.

**Was:** `finding.file` bzw. `f.severity` auf `null` wirft. Im Hauptpfad ist das nicht in try/catch, das Gate endet mit Exit 1 und Stacktrace. Fail-closed, aber unbeabsichtigt, und die Meldung ist ein Node-Stacktrace statt "reviewer unavailable".

**Beleg:** `echo '{"role":"x","verdict":"approve","findings":[null]}' | gate.mjs` → TypeError, Exit 1.

**Empfehlung:** `findings.filter(f => f && typeof f === "object")` beim Einlesen.

### F9 · Niedrig · `--issue <unbekannt>` ist ein stilles No-op

**Wo:** `auto-develop.sh:1053`.

**Beleg (S5):** `--dry-run --issue does-not-exist` → Exit 0, einzige Ausgabe ist die LINT/TEST-Warnung.

**Empfehlung:** Treffer zählen; ohne Treffer "issue X is not open in <source>" und Exit ≠ 0.

### F10 · Niedrig · Doku-Drift nach 1.0.16

- `prompts/pipeline-audit.md:22` (Punkt 15) und `references/pipeline-template.md:113` (Invariante 12) sagen, nur MEMORY.md werde aus dem Stash gerettet. Seit 1.0.16 rettet `preserve_paths` auch AGENTS.md, SOUL.md, SYSTEM.md, APPEND_SYSTEM.md, CLAUDE.md, `.pi/`, die Issue-Quelle und das Skript. Ein Audit nach Punkt 15 würde eine korrekte Pipeline für konform erklären, die nur MEMORY.md rettet.
- `SKILL.md:42` nennt den Commit-Schritt einen "marked stub". Im Approve-Zweig gibt es keine Markierung (siehe F2).

### F11 · Niedrig · Guard ohne Verhaltenstests

`tests/smoke.sh` typprüft `pipeline-guard.ts` und prüft per awk eine Kontrollflussstruktur. Die Regexe selbst werden nie gegen Beispiele getestet. F4 und F5 wären mit einer Tabelle aus zehn Kommandozeilen sichtbar geworden. Empfehlung: Patterns in ein kleines importierbares Modul ziehen oder einen Node-Test hinzufügen (Node 22+ kann `.ts` mit `--experimental-strip-types` laden; für einen Test reicht das).

### F12 · Niedrig · `npm@latest` im Release-Workflow

`.github/workflows/release.yml:156` installiert `npm@latest` unmittelbar vor `npm publish`. Der Workflow vermeidet sonst bewusst langlebige Tokens (OIDC). Eine gepinnte Major-Version (`npm@11`) schließt die Lücke, ohne Trusted Publishing zu verlieren.

### F13 · Niedrig · Irreführende Fehlermeldung bei einem gemappten Reviewer

`governance.mjs:334-336`. Mit genau einem gemappten Reviewer lautet der Fehler "uses a single provider (a); reviewers must span at least two". Das Problem ist nicht der Provider, sondern die Panel-Größe. `contract.md:113` beschreibt nur den Null-Fall als Warnung. Beleg: Config mit nur `review.security` → Exit 2 mit dieser Meldung. Empfehlung: eigene Meldung "only one review.* role is mapped".

### F14 · Niedrig · `ls -t` in smoke.sh

`tests/smoke.sh:1003` nimmt den jüngsten Implement-Prompt per `ls -t | head -1`. Die Dateien entstehen innerhalb weniger Sekunden; bei Dateisystemen mit Sekunden-Auflösung ist die Reihenfolge zufällig und die Assertion `(attempt 5)` flaky. Der Attempt-Tag (`a06`) sortiert lexikalisch korrekt; `ls | sort | tail -1` ist deterministisch.

## Was gut ist

- **Fail-closed ist konsequent gedacht.** Leerer Diff, unparsebare Reviewer, unbekannte Severity, Panel unter Floor, Master über blockiertem Gate, strictest-wins in beiden Parsern. Jede dieser Regeln hat einen Test.
- **pi-Flags stimmen.** `-p`, `--no-session`, `--no-tools`, `-t`, `-nc`, `--approve`, `--no-approve`, `--model provider/id:thinking`, `--thinking` existieren in pi 0.85.1 genau wie beschrieben.
- **Die Skill-Datei erfüllt die pi-Spezifikation.** `name` gültig, `description` 442 von 1024 Zeichen, `compatibility` ist ein erlaubtes Feld. Die Behauptung in `SKILL.md:29`, pi zeige den Skill-Pfad, ist korrekt: pi schreibt `<location>` in den System-Prompt und `References are relative to <dir>` in den Skill-Block. Die Prompt-Templates nutzen `${1:-default}`, das pi 0.85.1 unterstützt.
- **Die Doku ist ehrlich.** Drift Notes benennen das tote `max_split_depth`, das fehlende zweite Harness und die fehlende Generation-Eval. Das Threat Model in SKILL.md und README ist präziser als bei den meisten Tools dieser Art.
- **Die Test-Suite ist die eigentliche Stärke.** Rund 60 Szenarien gegen ein 1000-Zeilen-Bash-Skript, mit Stub-`pi`, die genau die Regressionsfälle der letzten Releases fixieren.
