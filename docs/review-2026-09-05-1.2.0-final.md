# Abschließendes Review vor 1.2.0

Stand: 2026-09-05, Windows, Node 26.8.1, installiertes Pi 0.85.1.

Nach den unten beschriebenen Fixes sind keine blockierenden Findings aus diesem
Review offen. Die lokale Prüfung ist bestanden. Der Release-Tag darf erst nach
grüner CI-Matrix auf dem Release-Commit gepusht werden; der Release-Workflow prüft
anschließend erneut und veröffentlicht über npm Trusted Publishing.

## Neue Findings und Korrekturen

1. **Hoch: JSON-Schemaqualität konnte ein kritisches Finding verdrängen.**
   Ein Block mit `verdict: "blocked"` und einem Critical wurde von einem zweiten,
   formal gültigen `approve` mit leerer Finding-Liste verdrängt. Die Sonde lieferte
   vor dem Fix `{ worst: -1, exit: 0 }`. Jetzt entscheidet die höchste Severity
   auch zwischen den Schema-Klassen. Beide Blockreihenfolgen sind getestet.
2. **Hoch: fehlgeschlagene Abschluss-Commits wurden nicht durchgehend als Fehler behandelt.**
   Ein einzelnes freigegebenes Issue konnte trotz abgelehntem Git-Commit Exit 0
   liefern. Beim Schließen eines Split-Parents wurde das Commit-Ergebnis ignoriert
   und das nächste Issue gestartet. Ein gemeinsamer Commit-Abschluss setzt nun
   einen Fehlerstatus und hält den Lauf an. Ein Halt nach dem letzten Child lässt
   den Parent offen. Freigegebene Änderungen und Checkboxen bleiben für einen
   manuellen Commit erhalten; sie werden nicht als abgelehnte Arbeit gestasht.
3. **Mittel: nicht-stringförmige Finding-Titel ließen das Gate abstürzen.**
   Die Schlüsselbildung normalisiert solche JSON-Werte, ohne die Severity zu
   verlieren. Zahlen und Objekte, auch mit eigenem `toString`-Feld, sind abgedeckt.

Die fünf neuen Fehlerszenarien waren vor den Fixes rot. Die Regressionstests in
`tests/unit/gate.test.mjs` und `tests/unit/completion.test.mjs` sind danach grün;
ein zusätzlicher Kontrolltest erhält den beabsichtigten Erfolg eines einzelnen
Issues mit `COMMIT_APPROVED=0`.

## Prüfung gegen echtes Pi

`tests/pi-live.mjs` ist ein wiederholbarer, ausdrücklich aktivierter Live-Test:

```bash
PI_LIVE_MODEL="openrouter/openai/gpt-5-mini:low" node tests/pi-live.mjs
```

Der Test packt das Paket und installiert das Tarball ausschließlich in ein
temporäres Projekt, ohne lokale SDK-Peers, globale Installation oder Änderung der
Pi-Einstellungen. Ergebnis:

- Das installierte CLI-Bin meldet `1.2.0`.
- Pi lädt die gepackte Extension samt Pi-/TypeBox-Imports.
- Der echte `pipeline_state`-Tool-Aufruf ist im JSON-Ereignisstrom nachgewiesen;
  die zurückgegebenen Zähler stimmen mit dem Fixture überein.
- Ein echter Reviewer erkennt die absichtlich entfernte Autorisierungsprüfung
  als Critical. Das deterministische Gate blockiert.
- Ein frischer, werkzeugloser Pi-Master-Prozess entscheidet `reject`.

Zusätzlich wurde ein isolierter werkzeugloser Pi-Aufruf mit exakt erwarteter
Antwort erfolgreich geprüft. Die Provider-Authentifizierung funktioniert.

Der generische Codex-Skill-Validator beanstandet ausschließlich das von Pi
unterstützte `compatibility`-Feld. Dieses Feld bleibt erhalten: Der maßgebliche
Pi-Skill-Loader meldet für den fertigen Skill keine Diagnostik. Der Einstieg bleibt
kurz; die Betriebsdetails stehen in den verlinkten Referenzen.

## Grenzen

Die breite Szenario-Suite benutzt Modell-Stubs. Der Live-Test prüft die echte
Paket- und Rollenintegration, keinen vollständigen Implementierungsdurchlauf mit
mehreren unabhängigen Providern. Der Claude-Code-Adapter bleibt nur gegen Stub und
CLI-Hilfe verifiziert. Die Qualität von aus einem PRD generierter Governance ist
weiterhin nicht durch einen Live-Eval belegt. Ein Guard ist kein Sandbox-Ersatz.
